Web 加载原理、性能检测分析与优化指南

页面迟滞如关隘，资源冗杂似贼兵。
缓存压缩齐上阵，神行太保快如风。

HTTP请求与响应的基本逻辑

想要优化好网站性能，我们必须了解一下加载逻辑，

不过在了解浏览器的加载流程之前，我们不妨先认识一下万维网之父——

Tim Berners-Lee

1989，英国计算机科学家蒂姆·伯纳斯-李（Tim Berners-Lee）提出了万维网的构想。到了 1990 年，他在 CERN 用一台 NeXT 计算机搭建了早期的 Web 服务器。

为了防止这台机器被人不小心关掉，他甚至在上面贴了一张醒目的标签：

“This machine is a server. DO NOT POWER IT DOWN!!”

一台不能随便关机的计算机，就这样成为了早期 Web 历史的一部分。

当然，现今的大家却早已习惯因特网的便捷，却很少地考虑背后发生的事情

那么…当我们敲下回车键时，背后究竟发生了什么？

找到 Server

一般地，当你按下回车键后，浏览器首先要确定访问的服务器的网络地址。对于常见的站点，浏览器就要通过 DNS 将域名解析为 ip 地址，如果浏览器及系统中没有可用的 DNS 缓存结果，通常就需要通过 DNS 查询获取目标 IP 地址。

当取到IP地址后 ，就可以尝试建立连接辣！对于常见的 HTTPS 网站，这通常还涉及 TCP 连接和 TLS 握手；如果使用 HTTP/3，则会采用基于 QUIC 的连接机制。

等这些准备工作完成，浏览器就可以发送 HTTP 请求，向服务器索取网页内容啦！

（゜ー゜）当然…这只是最简单最基本的情况，而且这种方式还涉及到一个小问题：

如果每次访问都要从头建立连接、查询域名、下载全部资源，岂不是会浪费不少时间？

所以，浏览器会利用 DNS 缓存和连接复用等机制减少重复开销 ；而 CDN 也能在合适的场景下，让用户从距离更近的节点获取资源。(这些机制我们会在后面慢慢聊)

Server 开始响应

当我们的请求到达后，服务器需要处理请求，并返回相应的 HTTP 响应。

对于一个普通的网页导航请求，响应通常会包含 HTML 文档。浏览器收到这些数据后，就能开始解析页面了。

从发出请求到收到响应的第一个字节，需要经历网络传输以及服务器处理等环节。性能检测中有一个重要指标叫作 TTFB（Time to First Byte），它关注的正是这一阶段的耗时 。

这里有一个Tips：服务器响应快，不代表整个网页一定加载得快；但如果响应迟迟未出现，后面的解析也会被拖慢。

至于如何判断 TTFB 是否正常，以及 CDN、服务器缓存能否改善这一过程，就留到后面再详细讲解啦喵！

浏览器解析

当 HTML 数据开始到达，浏览器就可以逐步解析它了喵~o( =∩ω∩= )m。

浏览器解析 HTML 时，会逐步构建 DOM（文档对象模型） ，把原本的文本标记转化成可以操作的节点结构。

与此同时，浏览器还可能发现 HTML 中引用的 CSS、JavaScript、图片和字体等资源，并根据具体情况发起额外请求。

例如，咱的主页引用了一张首页背景图、一份样式表，还有一些控制页面动画的 JavaScript。

这些资源并不一定要等 HTML 完全解析结束后才开始下载。有些请求可以提前发起，不同资源也可以并行获取。

但是，资源多了也不全是好事喵！如果页面引用了大量不必要的文件，或者某些资源阻碍了关键渲染过程，页面就可能迟迟无法呈现出完整的内容。

所以，后面咱们还需要了解如何观察资源请求，以及怎样判断它们是不是拖慢页面的原因。

接着，浏览器会开始解析 CSS ，构建 CSSOM（CSS 对象模型） ，再结合 DOM 计算元素的样式和布局。接着，它会根据页面的绘制需求，把文字、背景、图片等内容绘制出来，并在需要时进行图层合成，最终呈现在屏幕上。

还有一个值得注意的地方：某些 CSS 和 JS 会影响浏览器何时能够绘制页面。即使 HTML 已经下载完成，屏幕上也未必会立刻出现咱们最关心的内容。

因此，下载完成、开始渲染、主要内容出现，是三个不能简单画上等号的时刻。

所以在性能分析中，我们更应该关注页面何时呈现给访问者。

页面已经出现…就结束了吗？

不一定喵！

有些图片可能还在加载，有些 JS 还需要执行，而 User 也可能马上点击按钮、展开菜单或者切换页面。

如果 JavaScript 执行时间过长，就可能占用浏览器主线程，导致某些交互无法及时处理；如果图片没有预留合适的尺寸，加载完成后还可能把周围内容挤开，让页面突然发生布局偏移。

所以说，关于网站优化的这部分，其实有很深的学问的喵！

性能检测与指标分析

上一章我们已经大致地了解了浏览器加载网页的大致逻辑，

那么……一个显著的问题来了。

如果我们拥有一个自己维护的网站，那么我们应该如何判断它快不快呢？

总不能每次打开网页，都盯着屏幕凭感觉说一句“欸……好像还挺快的”吧？(￣▽￣”)

所以，本章我们就来认识几个 Web 性能检测工具，并尝试找出几个关键指标~

Chrome DevTools

打开自己的博客，按下键盘上的 F12，或者使用 Ctrl + Shift + I ，就能打开开发者工具了喵！

接下来，切换到 Network 面板。这里记录了浏览器在加载网页时发出的网络请求

我们需要重点关注四项指标：

  • Size

如果一个页面需要下载大量图片、脚本和样式表，那么这些资源就可能增加页面加载的网络开销 。

尤其是未经压缩的大图片 ，有时会成为拖慢页面加载速度的重要因素。

  • Time

它可以帮助我们观察每个资源请求花费了多长时间。

如果某个资源的请求时间明显长于其他资源，就值得进一步检查。

  • Waterfall

请求瀑布图可能是 Network 最值得关注的一部分了罢，瀑布图会按照时间顺序展示各个请求的执行情况。

通过它，我们可以十分直观并且可视化观察哪些资源先加载，哪些资源后加载，以及不同请求之间是否存在等待关系。

  • 浅灰色/透明斜线块：通常表示排队（Queueing/Stalled）。通常表示请求暂时处于等待状态，可能与连接资源、浏览器调度或请求优先级有关。
  • 绿色块：表示等待服务器响应（TTFB）。也就是请求发出去，到服务器返回第一个字节的时间。如果绿色块很长，说明服务器处理慢、网络慢或者 CDN 没命中。
  • 蓝色块：表示下载内容（Content Download）。如果蓝色块很长，说明文件太大，或者用户网速慢。
  • 条形图的左右位置：表示请求发起的先后顺序。如果原本可以并行的请求，因为 JS 阻塞变成了串行（像阶梯一样排下来），那就是优化的重点。

不过要注意：请求耗时长，并不一定意味着资源本身有问题。网络状况、服务器响应、缓存状态和请求优先级等因素，都可能影响结果。

  • Overview

时间轴概览直观地展示了所有网络请求随时间的分布情况。

图的左侧有一条蓝色的竖线，代表 DOMContentLoaded 事件触发的时间点；右侧有一条红色的竖线，代表 Load 事件触发的时间点。如果右侧的请求离红线很远，说明页面主体加载完后，还有非关键资源在慢慢加载。

当然，Network 面板的内容只适合在宏观层面粗略地浏览喵，但如果需要深入了解的话，我们就要进一步来到Performance 面板喵 ο(=•ω＜=)ρ⌒☆

打开开发者工具，切换到 Performance 面板。

接下来，点击录制按钮，然后重新加载页面。等待页面完成主要加载后，停止录制。

稍等片刻，浏览器就会生成一份时间线记录。

第一次看到这份记录时，可能会觉得有点眼花缭乱喵！(๑•́ ₃ •̀๑)就像年少的你第一次在 Minecraft 按下 F3 后看到满屏的不认识的英文单词一样罢

不过不用担心，我们只需要先认识几个重要区域。

  • Main

Main 是 Performance 面板中非常重要的一部分。

浏览器主线程承担着许多工作，例如：

  • 解析 HTML
  • 执行 JS
  • 计算元素样式
  • 进行页面布局
  • 执行部分绘制相关工作

这些任务会按照实际调度情况在主线程上执行。

在 Main 轨道里，你会看到很多像瀑布一样一层层叠起来的小方块，这叫火焰图（Flame Chart） ：

  • 横轴 代表时间 ：方块越长，说明这个任务花的时间越久。
  • 纵轴 代表调用栈（Call Stack） ：最上面的是父任务，下面的小方块是它调用的子任务。
  • 看哪里最宽 ：就找那种横跨特别宽、特别显眼的方块，那就是拖慢页面的“罪魁祸首”喵！

点击某个任务，还能进一步查看它的执行时间、调用关系以及相关代码位置。

例如，如果发现一段 JavaScript 占据了主线程很长时间，就可以继续查看它究竟来自哪个脚本文件，以及具体执行了什么操作。

这时候，我们就不再只是凭感觉说“页面好像有点卡”，而是有了进一步定位问题的线索( •̀ ω •́ )y。

  • Long Task

这里需要介绍一个重要概念：Long Task（长任务） 。一般地，在浏览器主线程上连续执行超过 50ms 的任务，就属于长任务。

为什么要关注它呢？因为浏览器主线程需要处理的不只是 JavaScript，还包括用户交互、样式计算和其他工作。如果某个任务长时间占用主线程，其他任务就可能无法及时执行。

例如：User 点击了主页上的一个按钮，但浏览器正在执行一段耗时很长的 JS。

那么，User 可能需要等待这段任务结束，才能看到按钮对应的反馈。这就是我们常说的主线程阻塞。

如果页面中存在大量长任务，就值得进一步检查 JavaScript 是否过于复杂、是否存在不必要的计算，或者能否将任务拆分成更小的部分。

一般地，如果你在 Main 里发现了红色的 Long Task，别慌，点它喵！点击后，在下方弹出的 Bottom-Up（自底向上）列表里，按 Self Time（自身耗时）排序。这时候跳在最上面、占用时间最长的那个函数，就是罪魁祸首啦！顺藤摸瓜就能找到是哪一行 JS 代码写得太重了喵~ (✧ω✧

需要注意的是，长任务不一定都会造成明显的卡顿，但它们是值得排查的重要线索哦~

  • Network

这和前面的 Network 面板有什么区别呢？

Network 面板更适合详细检查单个请求，而 Performance 面板则能够把网络活动与浏览器内部执行过程放在同一条时间线上观察。

例如： 某个 JS 脚本下载完成后，浏览器立即开始执行它；执行过程中又触发了大量样式计算和布局操作。

这时候，我们就可以把网络请求与主线程活动联系起来，理解页面为什么会在某个时间段出现卡顿。 这种观察方式对于分析复杂页面尤其有用<(￣ c￣)y▂ξ。

  • Timings

Performance 面板还会记录一些重要的页面加载时间节点。

例如：

  • FCP：首次内容绘制。
  • LCP：最大内容绘制。
  • DCL：DOMContentLoaded 事件。
  • Load：页面 load 事件。

这些时间点可以帮助我们理解页面在不同阶段的加载状态。

例如，如果 DOMContentLoaded 已经触发，但 LCP 仍然很晚才出现，就说明 HTML 解析完成并不代表主要内容已经及时呈现。

这时候，我们就可以进一步检查最大内容元素的资源加载、渲染时机以及相关依赖。

  • Layout shifts

如果页面在加载过程中突然发生位置变化，例如文字被挤到下面、图片突然撑开页面，那么就可能出现了 Layout Shift（布局偏移）。

  • 每一个菱形，代表页面发生了一次非预期的布局偏移 。

  • 菱形出现的位置，就是偏移发生的精确毫秒时刻。

  • 两个菱形之间的距离越近，说明页面在短时间内疯狂跳动，用户体验极差喵！( ≧Д≦)

  • Screenshots

Performance 面板还可以记录页面在加载过程中的截图喵o(￣▽￣)ブ。 这也是相对于那些奇怪的数据图是最便捷的方式了喵！

通过这些截图，我们能够观察页面在不同时间点呈现了什么内容。

例如： 页面已经开始显示背景和导航栏，但主要内容区域仍然空白。 又或者，页面主体已经出现，但某张图片迟迟没有加载完成。 这有助于我们理解性能指标背后的真实体验。

小结

通过 Performance 面板，我们可以从浏览器内部进一步寻找问题：

  • 页面是否存在长时间运行的 JavaScript？
  • 主线程是否被频繁阻塞？
  • 样式计算和布局是否过于频繁？
  • 页面是否出现意外布局偏移？
  • 主要内容究竟在什么时候呈现？

不过，Performance 面板提供的信息比较细致，第一次使用时不必试图理解每一个任务块。

先学会找到异常的时间段，再结合具体任务进行分析，就已经足够啦喵( •̀ ω •́ )✧！

GTmetrix

前面我们已经学会使用 Chrome DevTools 观察网络请求和浏览器内部的执行过程。

不过，如果想快速了解一个网站的整体性能表现，还可以借助第三方检测平台。而且能比看那些在 Chrome DevTools 奇奇怪怪的图表要节省脑细胞一些

这里介绍一个比较常见的工具——GTmetrix。

不过，GTmetrix 还有一个小缺点，FREE 版的用户只能免费使用五次 TwT，不过在你有多个邮箱的情况下，可以挨个注册账号，这样我们的使用次数就变成无限次辣！ψ(｀∇´)ψ

进入到 Dashboard 后，选择节点，设备以及速度限制后，就可以开始测试辣！

报告中包含 Performance（性能评分）、LCP、TBT、CLS 等信息。前面已经介绍过这些指标，这里就不再重复讲解了。

咱们更应该关注的是 Structure 中的 impact 部分，

GTmetrix 会用颜色和小标签，直观地告诉咱们每条建议的 impact

  • 图片没有经过适当压缩，导致资源体积过大。
  • CSS 或 JavaScript 文件存在不必要的开销。
  • 静态资源没有配置合适的缓存策略。
  • 图片或其他重要资源加载得不够及时。
  • 某些请求存在重定向或响应时间过长的问题。

点击具体的建议，通常还能看到相关说明、受影响的资源以及进一步的优化方向。

这里需要注意：GTmetrix 给出的建议是排查线索，而不是必须全部执行的优化清单。例如，某项建议可能只影响一个不重要的第三方资源；有些建议也可能与网站实际使用场景并不完全匹配。

因此，我们应该结合自己的页面结构和实际需求，判断哪些问题值得优先处理喵

基本的性能排查思路

讲了这么多，我们还需要掌握一个基本思路：

不要病急乱投医，得先找到造成问题的原因 。

一般来说，可以按照下面的思路进行排查：

  • 观察现象： 页面是打开缓慢、图片加载迟缓，还是交互时出现卡顿？
  • 查看报告： 结合 GTmetrix 的指标和优化建议，寻找可疑环节。
  • 定位问题： 使用 Chrome DevTools 检查具体请求、资源和浏览器任务。
  • 实施优化： 根据实际原因，选择合适的解决方案。
  • 重新测试： 在尽量一致的测试环境下对比优化前后的结果。

例如，如果发现 LCP 较高，可以先查看 GTmetrix 给出的相关建议，再利用 Network 确认首屏主要内容对应的资源是否加载过慢。如果发现 TBT 较高，则可以打开 Performance 面板，检查是否存在耗时较长的 JS任务。而如果 CLS 较高，就需要进一步检查图片尺寸、动态内容以及字体加载等因素。

记住： 性能优化不是为了让检测报告变得漂亮，而是为了让访问者获得更好的体验。

不要盲目压缩资源，也不要为了追求某个评分而随意修改网站。先观察、再定位、最后验证。

常见性能优化技巧

前面两章，我们已经系统性地了解了网站基本加载逻辑和性能分析，但是我们只有“发现问题”是不够的，光凭 GTmetrix 给出的提示也是不够的，本章我们来了解几个常见的性能优化技巧ヾ(≧ ▽ ≦)ゝ。

图片优化

上图我们可以看到，在相同画质的情况下， AVIF 的大小最小，但是 AVIF 格式发布时间较新，目前旧设备支持性较差……

所以… 综合来看选择 WebP 就好啦(￣▽￣)”

如果是简单的图标、Logo 或几何图形，可以考虑用 SVG 代替位图。

SVG 是矢量格式，用代码描述图形，无论屏幕多大、怎么缩放都不会模糊，体积往往只有几 KB。

但有些页面很长，如果一打开就加载所有图片，首屏之外的大量图片会白白占用带宽。懒加载 就是只加载用户当前屏幕能看到的图片，等用户往下滚动时，再加载后面的图片。

给 <img> 标签加上 loading="lazy" 即可，浏览器会自动处理的喵。

但资源加载需要分先后的哟。

  • 首屏关键图片（通常是 LCP 元素） ：不要加懒加载，还可以加上 fetchpriority="high"，让它优先下载。
  • 普通图片 ：正常排队即可，用 loading="lazy" 延迟加载。

当然，懒加载也不是所有图片都适用的。例如，页面顶部的 Logo、首屏背景图以及其他关键内容，如果也被设置为懒加载，反而可能延迟它们的出现。

所以，咱们需要根据资源的重要程度安排加载顺序，而不是简单地让所有图片都慢慢加载。另外，对于尺寸较大的图片，还可以使用 srcset 和 sizes，让浏览器根据设备屏幕和实际显示尺寸选择合适的图片版本，避免手机用户也要下载一张为大屏幕准备的高清图片。

总而言之，图片优化的核心并不复杂的喵！尽量减少不必要的数据传输，同时保证图片在实际显示时仍然具有足够的清晰度就好啦。q(≧▽≦q)

静态资源优化

图片处理完毕，接下来就轮到网页的样式表和脚本啦！

CSS 决定了页面的外观，而 JavaScript 则负责实现各种交互和动态效果。不过，如果它们的加载和执行方式不合理，也可能拖慢页面的呈现。

首先，我们可以检查是否存在没有使用的 CSS 和 JavaScript，及时删除不必要的代码。对于 JavaScript，还可以根据实际情况使用 defer 和 async 调整加载方式。


咱的HomePage-Haze主页就是这么设计哒

一般地，具有依赖关系的业务脚本通常更适合使用 defer，而不依赖其他代码的独立脚本则可以考虑使用 async。

此外，还可以通过代码拆分（Code Splitting）和按需加载，避免用户打开一个页面时就下载所有功能所需的脚本。

如果 Performance 面板发现 JavaScript 存在明显的长任务，也可以进一步检查是否有不必要的计算、频繁的 DOM 操作，或者能够拆分执行的复杂任务。

当然，CSS 也不能忽略。过于庞大的样式表、重复规则以及不必要的样式计算，都可能增加浏览器的工作量。对于首屏渲染非常重要的关键 CSS，可以考虑适当优化其加载方式；而非首屏所需的样式，则可以根据页面结构合理安排。

不过，这些优化都需要结合实际情况进行，千万不要为了追求性能而随意删除样式或脚本，最后把原本好好的页面弄得面目全非喵！性能与样式是平衡哒QwQ

缓存与 CDN 优化

如果说前面的优化主要是在减少资源本身的开销，那么缓存与 CDN 则是在想办法减少重复下载，以及缩短资源传输的距离。

首先是浏览器缓存：

对于图片、CSS、JavaScript 等不经常变化的静态资源，我们可以通过 HTTP 响应头中的 Cache-Control 设置合适的缓存策略。

这表示资源可以被公共缓存，并在一年内使用缓存版本。immutable 则表示在有效期内资源不会发生变化。

当然，在Cloudflare的Cache Rules里也可以设置喏哒！

这种配置更适合文件名包含版本号或内容哈希的静态资源。如果文件内容更新，也应该同步更新文件地址，避免用户长期使用旧版本。

在 HTML 文档中，使用 ?v=”版本号” 的形式可以破坏静态文件的缓存哟~

接下来就是 CDN。

CDN（内容分发网络）可以在不同地区部署边缘节点，将静态资源缓存到距离用户更近的位置。当用户请求资源时，如果对应节点已经缓存了资源，就可以直接返回，而不必每次都回到源站获取。

一般地，在全球范围内，最好用的免费的 CDN 提供商就是——CLOUDFLARE

减少不必要的资源请求

最后，还有一个容易被忽略的问题：网页是不是加载了太多根本用不上的东西？

例如，某些插件可能会在所有页面加载脚本，但实际上只有其中一个页面需要它；某些第三方统计、分享或动画脚本，也可能带来额外的网络请求和执行开销。

所以，定期检查网站引用的资源，删除不再使用的插件和脚本，也是一种非常有效的优化方式。

另外，字体文件同样值得留意。过多的字体字重、字符集和字体文件可能增加下载量，可以根据实际需求精简字体资源哦~。

小结

到这里，我们已经介绍了几种常见的网站性能优化方法：

  • 图片压缩与格式选择。
  • CSS、JavaScript 的加载与执行优化。
  • 浏览器缓存和 CDN。
  • 减少不必要的资源请求。

它们分别从资源体积、浏览器执行、网络传输和重复请求等方面改善网站性能。

当然，优化方法还有很多，但没有必要把所有技巧都应用到每一个网站上。

先找到真正的问题，再选择合适的解决方案，才是性能优化最重要的原则喵！。
